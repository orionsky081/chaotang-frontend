## 结论一：一个被推翻的诊断（最重要）

我们之前花了**两轮**，把「质门恒红」诊断成"缺证空跑"、"后端 prompt 烂"、"质门尺子歪"，还据此给后端加了输出纪律、给前端做了补证清单。

**真相是：模型不够强。**

| | 旧模型 `deepseek-chat` | 新模型 `deepseek-v4-flash` |
|---|---|---|
| finance 质量分 | 1.33 / 1.94 / 1.8 / 2.69 | **5.0 / 4.83** |
| 结果 | 次次 `release_gate=blocked` | 满分放行 |

同样的旨、同样的质门、同样的 prompt —— **换个模型，从必挂变成满分。**

那些改动不算错（诚实性护栏该加），但**我们一直在优化一个不是瓶颈的东西**。

> 教训：在你确认瓶颈之前，任何"优化"都是在猜。**先换一个变量，再改一行代码。**

## 结论二：② PACK 的 0.0 是假的 —— 质检员罢工被伪装成"你的方案 0 分"

`pack_rd` 报了 `质量门控未通过: 0.00 < 3.5`，下游两个蜂群连坐 skipped。我第一眼判定"PACK 蜂群坏了，这是唯一的真故障"。

**PACK 一直是好的。** 它 12 个字段全产出了，内容还挺硬 —— 算对了 `4×24×3.6V×3.5Ah = 1209.6Wh`，落在需求的 935~1265Wh 区间内。

倒下的是**质检员**：

```
QA agent 返回空串 ""
  → JSON 解析失败 (qa_result="error", raw_output="")
  → 没有 total_score
  → 旧代码 qs.get("total_score", 0) 默认成 0.0        ← 假事实在这里诞生
  → 门禁报「质量门控未通过: 0.00 < 3.5」               ← 假事实被当成质量结论
  → 下游全 skipped
```

`flow_engine` 里那处更直白，把静默回退**当设计写在注释里**：

```python
# quality_score 为 None/空时视为 0 分（确保门控触发）
```

**拦下游是对的**（没验过的产出不许往下流）。**错的是把事故说成质量差** —— 审计时永远分不清"没跑"和"跑了但很烂"，而两者的修法完全相反（修 QA vs 修产出）。

已修（commit `4ca8cc8`）：缺分独立成一类，报错说人话 ——

> **质检缺分**：上游 pack_rd 未产出 quality_score（QA agent 空输出/解析失败），**非产出质量差**。已按 fail-closed 拦下游，请查 QA 步而不是改产出。

真低分（③ 兵部 3.0 < 4.0）仍如实报分数，不会被误标成质检故障。

## 结论三：v4-pro 比 flash **更差**（反直觉）

拿同一道 PACK 换 v4-pro 重跑，跑了 **12 分钟才过 4~5 步**（flash 全程 86 秒），而且 **lint 失败率明显更高**：

```
15:52  cell_engineer            lint 失败(1错) → 重试2次仍1错 → 用最优输出
15:56  presale_cost_estimator   lint 失败(15错) → 自愈重试 → 16错（越修越坏）
```

**pro 在 18 步长链上失控。** 已杀掉，配置还原为 flash。

> **flash 才是这套蜂群的正确档位。** 你的 5.0 分是 flash 打出来的。
> 「更贵 = 更好」在这里不成立 —— 长上下文 + 结构化输出约束下，thinking 模式反而更容易跑偏。

## 结论四：一个定时炸弹 —— `quality_score` 双标度

- ①③④⑤⑥⑦ 用的是 **0~5 制**（5.0 / 3.0 / 4.09 / 4.83）
- ⑧⑨ 那条 6 蜂群链用的是 **0~1 制**（0.86 ~ 0.92）

**两套标度混在同一个字段里。** 任何读 `quality_score` 的代码都会误判 —— 0.92 在 0~5 制里是"惨败"，在 0~1 制里是"优秀"。

## 最该记住的一句

**0.0 这个数字骗了我。**

我看到它，脱口而出"PACK 根本没干活，这是唯一的真故障" —— 而它其实是个善意的默认值（"确保门控触发"），把事故伪装成了评分。

**一个为了方便而设的默认值，制造了一个假事实，然后这个假事实指挥了我的判断。**

这已经是同类问题的第二次了（上一次：`taskTitle()` 没给标题时拿机器指令当标题，一路裸奔进奏折）。

> 建议做一次系统性排查：**grep 全仓所有 `or 0` / `get(x, 0)` / `?? 0` 的默认值，逐个问"这个 0 是真的 0，还是'我不知道'？"**
> 凡是把"未知"写成"零"的地方，都在生产假事实。
> **默认值是这个代码库里最没人审查、却最会撒谎的东西。**
